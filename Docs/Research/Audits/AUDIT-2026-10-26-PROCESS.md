## 2. Как реально идёт работа

### 2.1 Что есть (и это неплохо)

- Есть формальная верификация и общая лексика: BUILD PASS / SERVER-LOG PASS /
  CLIENT/VISUAL / USER (`Docs/AGENT_HANDOFF.md` §1). Ложь о «прошло» встречается редко,
  `NOT RUN` честно фиксируется. Это сильная сторона.
- Есть настоящая автоматизация QA: headless loopback-сервер (`Tools/ClaudeQA/*`),
  `Tools/wb_log_report.py`, Triage (`Tools/SteelmillTriage/steelmill_triage.py`,
  контракт `summary.json` в `Docs/Research/SteelmillTriage/SUMMARY_CONTRACT.md`),
  demo-запись, unit-тесты C++/Python.
- Роли зафиксированы: Claude пишет gameplay-код и выносит вердикт; Codex собирает/
  гоняет QA/мержит BATCH-READY; DeepSeek — исследования и доки; owner — плейтест и
  решения D0xx. Есть согласование через почтовый ящик (`TO_CLAUDE.md`, `wait_mail.ps1`).

### 2.3 Распределение ролей и конфликты

- **Claude** (основной код, «Madd3st (via Claude)» в `git log`): gameplay-код, вердикты.
  Дублирует Codex там, где сам гоняет QA (см. `6a8c241c` «Authored in a Linux sandbox without
  MSVC» — код без сборки, который Codex потом собирает).
- **Codex** («C0xx» эксперименты): сборка/QA/merge. Топчется в общих файлах
  `Player.cpp`/`GameRules.cpp`/`ShotValidator.cpp`/`CMake` вместе с Claude — AGENTS.md
  это уже запрещает («One integrator owns shared … changes»), но на практике D013 решает,
  кто трогает gameplay.
- **DeepSeek/OpenCode**: research-ветки `warsbots/research/deepseek`, `movement-params`,
  `steelmill-triage` + worktree в `%TEMP%`. Хорошо изолировано, но ветки не мержатся и
  протухают.
- **Owner**: плейтесты + решения D0xx. Узкое место: каждая фича ждёт owner-плейтеста,
  а owner играет только когда захочет.

**Вывод:** роли в целом верны, но (1) Claude пишет без сборки, (2) общий код трогают оба,
(3) нет правила «кто интегрирует в main». Нужен один интегратор (Claude), Codex — только
build/QA/merge-по-команде, DeepSeek — только доки/исследования/разбор логов/генерация тестов.

### 2.4 Контракты и форматы

Есть контракт `summary.json` (`warsbots-run-summary/1`), есть demo-запись, есть `wb_log`
уровни. Нет: (1) контракта на «как агент ставит задачу» (структура задачи: цель → файлы →
приёмка), (2) контракта на «как агент сдаёт результат» (сейчас — раздутые STATUS/AGENT_HANDOFF).
Модель «mailbox» формальна, но не читается машиной на входе в задачу.

### 2.5 Тестирование: от «написал» до «работает»

Путь сейчас: код → сборка ON+OFF (~2–3 мин из-за `version.h`) → unit → headless 6×120 или
15×660 → парсинг → вердикт → owner-плейтест → (возможно) merge. Итоговая задержка — часы на
кандидата, из которых собственно «проверил, что работает в игре у человека» — только последний
шаг, и он выполняется редко. **Клиентская репликация N ботов, два одновременных клиента,
bot-vs-human на текущей ветке — не проверены вообще** (`STATUS.md` L51-58).

## 5. Экономия лимитов

### 5.1 Где горят токены

1. **Пересборка всего CryGame на каждый коммит** (`version.h` = git describe, ~2–3 мин и большой
   diff компиляции). → Не трогать `version.h` на doc-коммитах; копить правки в один билд.
2. **Прогоны 15×660 c (11 мин) на каждую итерацию** вместо короткого 6×120 c smoke. → 15×660
   только для финальной приёмки, не для каждого кандидата.
3. **Повторы из-за шума gate** (P4). → медиана по 3, порог ±15%.
4. **Раздутые доки**: STATUS 644 строк, AGENT_HANDOFF 666, TO_CLAUDE 80 КБ. → сжатые «сейчас»-файлы,
   история в `Experiments/`.
5. **Перечитывание всего проекта**: агенты читают старые чек-ауты и старые STATUS (P2). → один
   чек-аут, `STATUS.md` 10 строк, точные пути в постановке задачи.
6. **Длинные сессии** (облачная сессия Claude писала код без MSVC — потом переделка). → сессия =
   одна задача, с явным «собрать до конца».

### 5.2 Распределение по цене и силе

| Агент | Что должен делать | Что НЕ должен |
|---|---|---|
| **Claude** (дорогой, сильный в коде) | gameplay-код, интеграция в main, вердикты, фикс P0/P1 | гонять QA, парсить логи, писать доки, считать метрики |
| **Codex** (средний, упорный) | сборка ON/OFF, headless QA, merge BATCH-READY, приёмка по готовым критериям, ревью диффа | придумывать архитектуру, трогать общий код без D0xx, писать доки |
| **DeepSeek/OpenCode** (дешёвый, сильный в тексте/анализе) | доки, разбор логов, генерация unit-тестов/фикстур, исследование API, этот разбор, метрики-отчёты, Triage-скрипты | писать gameplay-код (нет MSVC-проверки), менять общий код, гонять игру |
| **Owner** | плейтест, решения D0xx, разметка карт, запись демо | сборка, QA, чтение логов |

### 5.3 Правила экономии

- Сессия агента = одна задача, с полными путями к файлам и критерием приёмки в постановке.
- Между задачами — `compact`/`clear`, не тащить историю.
- `AGENTS.md` — до 60 строк; `STATUS.md` — только «сейчас»; подробности — в `Experiments/`.
- Ревью только диффа (`git diff` ветки против `warsbots/main`), не всего файла.
- Мерж в `warsbots/main` каждые 2–3 дня, чтобы не копить merge-ад.

### 5.4 Что делать, когда агент упёрся в лимит

- Claude упёрся → Codex собирает/гонит QA по уже написанному диффу; DeepSeek готовит
  unit-тесты и разбор логов. Не начинать новую gameplay-фичу.
- Codex упёрся → Claude/DeepSeek готовят следующие задачи и доки, но не гоняют QA.
- DeepSeek упёрся → ничего критичного не блокируется (доки/исследования некритичны).
- Главное правило: **не начинать новую gameplay-работу, пока предыдущий дифф не собран и
  не замержен в `warsbots/main`.** Незавершённый дифф — это токсины, которые потом дорого
  перечитывать и чинить.

## Рабочий цикл на одну задачу (посильно одному человеку)

1. **Постановка** (owner/DeepSeek, 1 сообщение): «Задача X. Файлы: `Code/CryGame/Bots/BotNav.cpp`.
   Сделать: jump-рёбра Strength. Приёмка: `wb_nav` показывает рёбра типа Jump; 6×120 c без
   crash; owner видит прыжок. Не трогать: Player/GameRules/сеть.»
2. **Claude**: реализация + `Build-WarsBots.ps1 -Experimental` до BUILD PASS.
3. **Codex**: `-Experimental` ON+OFF build → headless 6×120 c → `wb_log_report.py` →
   один отчёт (не письмо-вердикт). Критерий PASS/FAIL фиксирован в постановке.
4. **DeepSeek**: (опционально) разбор лога/метрик, генерация unit-теста.
5. **Owner**: плейтест по чек-листу из постановки (5 пунктов).
6. **Merge** в `warsbots/main` при BUILD PASS + SERVER-LOG PASS + owner «да».

**Definition of Done:** собрано ON+OFF; headless QA без crash; метрика в допуске из
постановки; owner-плейтест подтвердил; замержен в `warsbots/main`; `STATUS.md` обновлён
(10 строк) и `AGENT_HANDOFF.md` переписан сжато.
