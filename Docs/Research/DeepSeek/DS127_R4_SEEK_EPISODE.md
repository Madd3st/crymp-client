# DS-127 — R4: жизненный цикл эпизода поиска оружия/боезапаса

Задача: DS-127 / C-157 (R4), назначена координатором 2026-10-30.
Источник кода: `warsbots/feature/claude-sprint` @ `307037bc08050d39f26310dc6cc7071dddddf4a6`.
Уровень доказательств: **чтение исходников**. Игра, сервер, сборка, прогоны и живые данные не
использовались. Ничего не реализовано, ничего не изменено в `warsbots/feature/*`.

Важно: это R4 из аудита владельца 29.10 (deadline поиска оружия). Исторический refactor-R4
`b902dfb4` («delete dead flags») — другая, уже закрытая задача; номера совпадают случайно.

## 1. Вердикт

Дефект подтверждён, и он шире, чем «окно привязано к жизни». В `UpdateWeaponSeek` есть
**два независимых отказа**, оба следуют из одного и того же места — таймер эпизода
отсутствует, а его роль играет `m_weaponSearchStarted`, поставленный в `ResetLife`:

- **A. Бесплатный SCAR вместо реального подбора.** Как только жизнь длиннее 6 с, ветка
  преследования (`elapsed < 6`) недостижима. При первом же опустошении боезапаса бот
  получает test-SCAR, даже если `FindNearby` только что нашёл доступный предмет в трёх
  метрах. Найденная цель при этом молча теряется.
- **B. Вечная потеря боеспособности.** После того как fallback уже израсходован, каждая
  итерация попадает в третью ветку: `m_weaponTarget = 0`, `WBI(move,false)`. Поиск
  находит кандидата, и в том же тике он обнуляется; бот стоит, не подходит и не подбирает
  до смерти, `wb_bot_stop` или перезапуска AI. Это и есть «устойчивая потеря
  боеспособности» из аудита.

Наивная правка «переставить `m_weaponSearchStarted = m_now` при опустошении» закрывает
только A и первые 6 с из B: через 6 с бот снова уходит в третью ветку и замирает. Нужен
именно жизненный цикл эпизода, а не новая начальная точка у того же таймера.

Разбор сценария A (жизнь началась в `t=0`, боезапас кончился в `t=100`):

1. `SelectAvailable` → `false`, огонь стоп.
2. `m_now>=m_nextSearch` (равен 0) и цели нет → `FindNearby` находит предмет, `m_nextSearch=102`.
3. `item != 0`, но `100-0 >= 6` → ветка `:756` ложна.
4. `:767` `!m_fallbackGiven && (!item || elapsed>=6)` → истина → `m_fallbackGiven=true`,
   `GiveTestSCAR`. Предмет, который бот видел, отброшен без единой попытки подойти.

Разбор сценария B (`t=140`, fallback уже выдан):

1. `:747` снова находит предмет, `m_weaponTarget != 0`.
2. `:756` ложно (`140-0>=6`).
3. `:767` ложно (`m_fallbackGiven` истинно).
4. `:773` обнуляет цель, `WBI(move,false)`, `Change(SEEKING_WEAPON)`.
5. Через 2 с (троттлинг) всё повторяется. Подбора не будет никогда.

Дополнительно:

- **Дальность против бюджета.** Радиус поиска 30 м, а 6 с при штатных скоростях (walk 1.30,
  run 2.50, sprint 5.46 м/с по проверкам проекта) покрывают 7.8 / 15 / 33 м. Верхняя
  половина собственного радиуса поиска физически недостижима внутри бюджета — то есть
  «истёк deadline» не означает «предмет недостижим».
- **Отказ подбора.** `PickUp` вернул `false` → цель просто обнуляется (`:763`), предмет не
  помечается; через 2 с он же будет выбран снова. `m_badItems` (`BotBrain.cpp:140-151`)
  для этого пути не используется, и его TTL 90 с для такой ситуации слишком велик.
- **Внешняя дозарядка.** Если оружие появилось извне, `SelectAvailable` вернёт `true` и
  функция выйдет корректно, но `m_fallbackGiven` и старый `m_weaponSearchStarted`
  сохранятся, поэтому следующее опустошение в той же жизни снова даёт сценарий B.
- **Отказ гранта.** `GiveTestSCAR` может вернуть `false` (например, клип не создался), но
  `m_fallbackGiven` уже выставлен (`:770`) — повторной попытки нет, дальше B.
- **SOCOM QA** (`:736-740`) выходит раньше и этим путём не затрагивается.
- **C153/DS-097** исправляли lifecycle цели *upgrade* (`BotWeaponGoal.h`, `UpdateUpgrade`),
  а не `UpdateWeaponSeek`; подтверждать «всё оружие исправлено» нельзя.

## 3. Минимальный устойчивый жизненный цикл

Принцип: **два разных таймера вместо одного**. «Когда отдать единственный fallback» — это
решение по эпизоду; «когда прекратить преследование» — это прогресс/бюджет цели. Смешивать
их в одном числе и есть текущая ошибка.

Состояние (минимум, `BotBrain.h`):

- `float m_seekStart = 0;` — 0 означает «эпизод закрыт» (заменяет смысл `m_weaponSearchStarted`).
- `float m_seekBestAt = 0, m_seekBestDist = 1e9f;` — прогресс преследования.
- `float m_seekCooldownUntil = 0;` — пауза между эпизодами.
- без изменений: `m_fallbackGiven` (строго один на жизнь), `m_weaponTarget`, `m_nextSearch`,
  `m_previousWeaponClass`.
- отказ подбора: `MarkBadItem(id, ttl)` с TTL 5 с (расширить существующий
  `BotBrain.cpp:146-151` параметром со значением по умолчанию 90 с, чтобы upgrade-путь не
  изменился), а не отдельный массив.

Правила (все — внутри `UpdateWeaponSeek`, порядок важен):

| № | Условие | Действие |
| --- | --- | --- |
| R1 | `SelectAvailable` истинно | закрыть эпизод (`m_seekStart=0`, `m_weaponTarget=0`, сброс прогресса), `return false`. Fallback не расходуется. |
| R2 | эпизод закрыт и `m_now>=m_seekCooldownUntil` | открыть эпизод: `m_seekStart=m_now`, `m_nextSearch=m_now`, `m_weaponTarget=0`, `m_seekBestAt=m_now`, `m_seekBestDist=1e9`. |
| R3 | эпизод закрыт (кулдаун) | `return false` — обычное поведение (roam/патруль) продолжается; бот не стоит на месте. |
| R4 | эпизод открыт, цели нет, `m_now>=m_nextSearch` | `FindNearby` (30 м, как сейчас), `m_nextSearch=m_now+2`. |
| R5 | цель есть, но `!AvailableForPickup` | цель в 0 (как сейчас, `:750-754`), эпизод не закрывать. |
| R6 | цель есть, в пределах 2 м / 2.2 м по Z | `PickUp`; успех → закрыть эпизод, `m_previousWeaponClass`, `SEARCHING_ENEMY`, `return true`; отказ → цель в 0 + `MarkBadItem(id,5)`. |
| R7 | цель есть, дальше | прежнее движение (`Steer`/`TravelGait`), обновить `m_seekBestDist/m_seekBestAt` при улучшении. |
| R8 | `!m_fallbackGiven && m_now-m_seekStart>=6` | выдать fallback один раз (`m_fallbackGiven=true`), закрыть эпизод. |
| R9 | `WeaponGoalExpired(m_now,m_seekStart,m_seekBestAt,8,60)` | закрыть эпизод; `m_seekCooldownUntil=m_now+10`. |
| R10 | эпизод открыт, кандидатов нет и `m_fallbackGiven` | закрыть эпизод сразу (без ожидания 60 с), `m_seekCooldownUntil=m_now+10`; не стоять в `SEEKING_WEAPON` весь бюджет. |
| R11 | `ResetLife` | `m_seekStart=0`, `m_seekCooldownUntil=0`, `m_fallbackGiven=false`, прогресс сброшен. |

`WeaponGoalExpired` уже существует и покрыт тестами (`BotWeaponGoal.h:24-30`,
`Tests/BotWeaponGoalTests.cpp`), поэтому переиспользуется без новой арифметики: 8 с без
прогресса, 60 с всего.

Почему так, а не иначе:

- 6 с остаются числом из аудита, но означают «пора отдать fallback», а не «перестать идти».
- После израсходованного fallback эпизод не длится вечно и не блокирует поведение: 60 с
  преследования → 10 с обычной жизни → новый эпизод. Бот продолжает двигаться и может
  наткнуться на оружие.
- R10 убирает стояние на месте: при отсутствии кандидатов ждать нечего.
- R1 гарантирует, что внешняя дозарядка не расходует fallback и закрывает эпизод.

Инварианты, которые нельзя нарушать:

- `m_fallbackGiven` меняется только в `ResetLife` и в R8 — не более одного гранта на жизнь.
- Никаких `SetPos`/импульсов/телепорта: движение только через `WBI_MOVETO`/`Steer`/`TravelGait`.
- Подбор только через `BotWeapons::PickUp` (нативный `IItem::PickUp`, лог `REAL PICKUP`).
- 10 Гц и существующий `m_nextSearch`-троттлинг сохраняются; поиск не чаще, чем сейчас.
- `Change()` остаётся единственным писателем состояния; SOCOM QA (`:736-740`) — без изменений.
- Флаг не нужен: это исправление дефекта, а не новая возможность. Если ревью потребует
  диагностический флаг, он обязан иметь дату выхода (правило net-zero).

## 5. Runtime-приёмка (позже, только после явного разрешения владельца)

Сейчас не запускается. Критерии на будущий batch, чтобы оракул не подменял игру:

1. Долгая жизнь (> 6 с) → боезапас в ноль → на карте доступное оружие → лог
   `REAL PICKUP … acquired=1`, возобновление огня, и **ни одного** `TEST GRANT SCAR`
   в этом эпизоде.
2. Fallback уже выдан в этой жизни → снова в ноль при наличии предмета → подбор и огонь;
   второго гранта за жизнь нет.
3. Пусто на карте и fallback израсходован → бот не стоит: движение/патруль продолжаются,
   поиск не чаще 1 раза в 2 с, нет потактового «нашёл-обнулил».
4. Регрессия: SOCOM QA-прогон не изменился; штатный спавн с SCAR fallback работает.

## 6. Что осталось недоказанным

- Частота сценария B в живых матчах не измерена (нужны логи `WEAPON GOAL`/`TEST GRANT` из
  существующих прогонов; новых прогонов для этого не требуется).
- Не проверено, насколько часто `GiveTestSCAR` реально возвращает `false` — путь R8b
  описан по коду, без статистики.
- 10 с кулдаун и 8/60 с бюджета — предложение, а не измеренная величина; они выбраны так,
  чтобы покрыть 30 м при run-скорости и не блокировать поведение.
