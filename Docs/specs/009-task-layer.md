## Что должно измениться
Сейчас у бота нет одной «текущей задачи». 15 мест выбирают, куда идти, и 7 мест потом эту цель переписывают. Кто кого глушит, записано попарно в разных функциях. Командир не узнаёт, что бот бросил приказ.

После этой спеки у бота одна активная задача с номером, владельцем, режимом движения и правилом для боя. Кто из исполнителей молчит — одна функция. На уровне 1 бот ведёт себя так же, как при 0, а лог показывает, кто его ведёт. На уровне 2 командир получает «не могу» по конкретному приказу и перестаёт держать бота на невыполнимой точке.

## Что вводим

**Структура `BotTask`** (новый `BotTask.h`, без движка):
- **Номер** `id`: счётчик на бота, растёт при каждой новой задаче, не обнуляется ни смертью, ни `Start()`, ни сменой уровня; 0 — задачи нет.
- **Номер приказа** `order`: выдаёт командир (счётчик на команду), у остальных владельцев 0.
- **Владелец** `TaskOwner`: лестница, QA-тест, QA-SOCOM, первый ствол, арбитр, лут, снайперская позиция, захват PS, приказ командира, удержание (#44), блуждание, бой, нырок (#41), техника (резерв, писателя нет до SPEC-006).
- **Режим движения** `MoveMode`: пешком / стоять / плыть / в технике.
- **Правило для боя** `CombatPolicy`: `Yield` — бой сбрасывает задачу (блуждание, лут); `Resume` — бой откладывает, потом возврат (приказ, удержание; заменяет `m_psHoldBack` из #44); `Keep` — бой не отбирает движение (лестница, нырок, позже техника).
- **Цель, время старта, причина сброса.**

### Жизненный цикл задачи

Блокер 2. У бота два слота: активная задача и не больше одной отложенной (только `Resume`).

| Событие | Что происходит | Лог |
| --- | --- | --- |
| `SetTask`, тот же владелец, та же цель (≤ 0,5 м) и тот же `order` | ничего, `id` прежний | — |
| `SetTask`, тот же владелец, новая цель или новый `order` | старая сброшена `replaced`, новый `id` | `drop`, `set` |
| `SetTask`, другой владелец (не бой) | старая сброшена `preempt`; отложенная, если была, сброшена `superseded`. Кто побеждает — прежний порядок в `Update` | `drop`, `set` |
| `SetTask(бой)` поверх `Yield` | старая сброшена `combat` | `drop`, `set` |
| `SetTask(бой)` поверх `Resume` | старая уходит в отложенные, `id` сохраняется | `suspend`, `set` |
| `SetTask(бой)` поверх `Keep` | отказ: бой стреляет, движение у прежней задачи | — |
| Бой кончился, есть отложенная | Возврат, только если источник её подтверждает: для приказа `order` равен текущему приказу командира этому боту. Иначе сброс `stale`, и писатель ставит новую обычным путём | `resume` или `drop` |
| Успех | владелец вызывает `CompleteTask(id)` | `drop reason=done` |
| Отмена владельцем, исполнителем, поздним callback | `CancelTask(id, reason)`. `id` не равен активной и отложенной — ничего не делает | `drop` или `late id= ignored` |
| Смерть / `ResetLife`, `Stop`, конец уровня, смена флага | `ClearTask(reason)`: оба слота, слот очереди, состояние нырка. Повторный вызов ничего не делает и не пишет | `drop` один раз |

Отдельные случаи:
- **Смена приказа в бою.** Командир выдал новый `order`, пока старый отложен. После боя сверка не сходится → `drop reason=stale`; бот идёт по новому. Старый приказ не возвращается.
- **Смерть.** `ClearTask(death)` чистит оба слота. Счётчик `id` не обнуляется, поэтому callback от прошлой жизни (`CancelSubSwim`, конец лестницы, `CannotReach`) приходит с чужим `id` и игнорируется.
- **Флаг 1→0 на ходу.** `ClearTask(flag_off)` на первом тике, дальше старый код. 0→1: слоты пусты, первый писатель ставит задачу. 1↔2: командир забывает свои 30-секундные запреты.
- **Конец уровня.** `ClearTask(level_end)`; командир чистит таблицу приказов и запретов.
- **Поздний ответ командиру.** `TaskResult` несёт `(bot, order)`. Командир применяет его, только если это текущий приказ бота; устаревший отказ новый приказ не снимает.
- **Часы.** Сроки слоя считаются по времени сервера, не по `m_now`: `Start()` обнуляет `m_now` (:391), а сроки переживают его.

**Запись цели.** Все 15 писателей пишут через `SetTask(owner, goal, mode, policy, order)`. Он ставит `m_intent` так же, как сейчас. Порядок владельцев в `Update` не меняется: слой не арбитр.

**Лог.** Номер есть в каждой строке, смена цели внутри владельца видна:
- `TASK set bot= id= order= owner= mode= goal=` — при каждом новом `id`. У боя цель — враг, новый `id` только при смене врага; у блуждания — при новом выборе точки;
- `TASK suspend|resume bot= id=`;
- `TASK drop bot= id= order= owner= reason= age=`;
- `TASK result bot= id= order= result=` и `TASK late bot= id= ignored`;
- в FRAME-сводке: новых задач и смен владельца на бото-минуту.

### Уровень 2

**Ответ командиру.** Владелец «приказ» при отказе (`bot_unreachable`, таймаут, общий бан связи на пути) шлёт `TaskResult::CannotReach(bot, order, point)`. Командир снимает этот приказ и 30 с не даёт боту ту же точку. Нет другой достижимой точки — бот блуждает в своей компоненте навмеша, а не идёт в недостижимое.

**Бан связи.** Сейчас первый `LADDER failed` банит связь для всех до конца уровня (`CancelLadder(...,true)` → `BanLink`, :2068 → :2000), jump-связь — после двух сбоев любых ботов, тоже навсегда (`m_linkFails` не убывает, :2150–2151).
- Обход одним ботом после его сбоя (цена ×50 на 30 с) — код PR #52 (`wb_bot_ladder_ban`, владелец 11.11). Уровень 2 его не дублирует.
- Общий бан — только после сбоев **двух разных** ботов за 120 с; повторы одного бота не считаются (иначе бот у единственного выхода банит его сам за три попытки). Снимается через 120 с, компоненты пересчитываются.
- Ключ бана — связь и направление: вверх и вниз — разные записи; соседняя связь не страдает.
- Кэш достижимости командира (`BotPSCapture.cpp:369,425`) перестраивается при бане и при снятии.
- Смена уровня или хеша навмеша снимает все баны.
- Лог `LINK ban link= dir= scope=bot|level bot= until=` и `LINK unban`; владелец получает `TASK drop reason=link_banned`.

## Приёмка на сервере

Блокер 3. «Стартов лестницы > 0» и «NAV fallback ниже» не доказывают выход: в Shore-02 после бана один бот поднялся, остальные остались отрезаны. Поэтому:

1. **Абсолютные ворота D-061 обязательны в каждом окне этой спеки** (600 с, Shore-15, оба значения флага):
   - стоят ≤ 20 % живых бото-секунд в каждой команде;
   - США на суше к 4 мин после готовности ≥ 6 из 7;
   - 0 ботов в круге 10 м дольше 60 с подряд;
   - p95 `PATHTIME` по итогу окна ≤ 2,5 мс.
2. Окно, где ворота не проходит значение 0, для приёмки **недействительно** (не PASS): уровень 1 по построению повторяет базу, а dev сегодня ворота не проходит (суша и круги FAIL, Shore-02 и 38e63072). Слой принимается только на базе, прошедшей ворота.
3. **Уровень 1 против 0:** стоящие по командам, NAV fallback и p95 в пределах ±20 % от 0; смен владельца на бото-минуту — записано как база для SPEC-006.
4. **Уровень 2 против 1:**
   - ворота п. 1;
   - США на суше не хуже уровня 1;
   - ни одного бота, которому та же точка выдана > 1 раза за 30 с;
   - ни одного отрезка, где связь закрыта для всех дольше 120 с;
   - `bot_unreachable` на бото-минуту ниже уровня 1.
5. Метрики аудита 14.11 (`Docs/Research/2026-11-14-audit.md`) добавляются в окно, когда войдут в ворота решением владельца; до тех пор считаются и печатаются без PASS/FAIL.
